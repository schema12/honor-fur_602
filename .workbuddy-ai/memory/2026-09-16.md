### 分区布局（expand(114m)，来自 U-Boot mtd-layout layout@1）
```
nmbm0: 1024k(bl2) 512k(u-boot-env) 1920k(factory) 128k(Trace)
       2048k(fip) 116736k(ubi)
```
= 0x0000000 bl2(0x100000) / 0x100000 u-boot-env(0x80000) / 0x180000 factory(0x1E0000)
  / 0x360000 Trace(0x20000) / 0x380000 fip(0x200000) / **0x580000 ubi(0x7200000 = 114MiB)**

另有 layout@0 "default"（stock 64m ubi + Tracebak + foxfs），需多布局 U-Boot。

### 关键结论：U-Boot 实际 boot 路径（决定 image 格式）
`mtd_boot_image()` @20230718 mtd_helper.c:
1. `get_mtd_device_nm("kernel")` — 若 mtdparts 中存在名为 `kernel` 的 **MTD 分区**，则走 `boot_from_mtd(mtd_kernel, 0)` → **直接启动裸 FIT**
2. 否则 `get_mtd_device_nm("ubi")` → `boot_from_ubi(mtd)` → 读 UBI 卷 `kernel` 的 FIT

而 24.10 的 `scripts/ubinize-image.sh` 生成 UBI 卷名为 **`kernel` + `rootfs` + `rootfs_data`**（KERNEL_IN_UBI=1 时）。
→ **必须使用 `KERNEL_IN_UBI := 1` + `IMAGE/* := sysupgrade-tar`（UBI2/TAR 路径），
   U-Boot 会自动把 TAR 内 kernel/rootfs 写成 UBI 卷 `kernel`/`rootfs` 并重建 `rootfs_data`。**
→ 若改用 `sysupgrade.itb` + `rootdisk=<&ubi_rootdisk>`（fitblk），U-Boot 需要 UBI 卷名 `fit`，
   与 ubinize 实际产物不符 → **不可行**（除非另配 UBOOTENV_IN_UBI 迁移，风险高）。

### 必须修正的错误（当前仓库 vs 24.10 原生结构）
1. **缺 fitblk 链路** — 24.10 mt7981 有两条路线：FIT+fitblk（新增）或 UBI1/UBI2（旧）。本设备走 UBI2/TAR，**不能**加 `rootdisk`/`u-volume-fit`。
2. **DSA 差异**：
   - 正确 mdio 标签应为 `switch@1f`（IM 24.10 全库 50 处用 `switch@1f`，`switch@0` 为 0 处）
   - `port@6` 正确含 `label = "cpu"`，不要 `phy-mode`（=2500base-x 由 gmac0 侧定义）
   - 24.10 用 `label-mac-device = &gmac0` 而不只是 nvmem-cells
3. **LED 定义方式**：24.10 用 `function`/`color` 属性（`LED_FUNCTION_STATUS`），旧的 `label = "green:status"` 过时
4. **`/ ` 节点名**：`leds` → `gpio-leds`，按键 `reset` → `button-reset`（24.10 惯例）
5. **缺 `u-boot-env` 的 mtd-mac / env 工具链**：24.10 有 `uboot-envtools`
6. **NMBM 写法**：24.10 用 `&spi_nand` 引用 + `mediatek,nmbm` + SPI 校准（`spi-cal-*`），
   旧写法直接内联 spi-nand 且无校准块
7. **02_network 锚点不匹配** — 旧的 `tenbay,wr3000k` 锚点在 24.10 中**不存在**（已改名/移除），
   需改锚点为实际存在的行；且 24.10 需在 `mediatek_setup_macs` 中处理 MAC
8. **缺 kernel config fragment** — 未处理 tc/SQM/IFB/CAKE/monitor 等能力显式保留
9. **DEVICE 定义缺** `DEVICE_DTS_DIR`、`SUPPORTED_DEVICES`、`DEVICE_VENDOR` 规范化
10. **CI 缺编译前断言** — 旧 workflow 只做 grep 不 fail；无编译后验证；无 manifest

### hanwckf 权威 DTS 揭示的硬件事实（补充）
- 兼容串: `"honor,fur-602", "mediatek,mt7981"` / model `"HONOR FUR-602/603"`

  - **这是 OpenWrt 5.4 时代 hanwckf 的写法**

  - → 用 24.10 原生 `mediatek,nmbm` 写法（用户要求"尽量接近原生结构"）

  - port6 = CPU（接 gmac0）
  - port5 = 也 2500 fixed-link（内部 2.5G 口 / 未引出）

- **`&hnat` 节点**：hanwckf 专有（mtk-openwrt-feeds HNAT 驱动），
  `mtketh-wan="eth0.2"` `mtketh-ppd="eth0.1"` `mtketh-lan="eth0"` `mtketh-max-gmac=<1>`
  → **ImmortalWrt 24.10 主线无此节点，必须删除**（HNAT 是 mtk 私有加速，用户要原生 mac80211/mt76）

### ImmortalWrt 24.10 原生结构（已实拉核对）
- `KERNEL_PATCHVER := 6.6`，`SUBTARGETS := filogic mt7622 mt7623 mt7629`
- `target.mk`: `DEFAULT_PACKAGES += fitblk kmod-phy-aquantia kmod-crypto-hw-safexcel wpad-openssl uboot-envtools bridger`
- **24.10 全部使用 DSA**（`&switch { ports { port@N { label="lanN" } } }`），无 02_network 接口映射
  - DSA 端口名来自 DTS `label`，**02_network 不再需要**（用 `label-mac-device` 处理首 MAC）
- `mdio_bus` 上交换机节点：**24.10 全库 50 处用 `switch@1f`，0 处用 `switch@0`**
- `chosen` 需 `bootargs-append = " root=/dev/fit0 rootwait"` + `rootdisk = <&ubi_rootdisk>`（FIT/fitblk 路线）
- `ubi` 分区需 `compatible = "linux,ubi"` + `volumes { ubi-volume-fit { volname="fit" } }`
- **⚠️ 重大冲突（必须解决）**：
  - 24.10 的 FIT 路线要求 UBI 卷名 **`fit`**（fitblk 挂载 `/dev/fit0`）
  - 但 U-Boot `mtd_boot_image()` 与 `write_ubi2_tar_image()` 需要 UBI 卷名 **`kernel` / `rootfs` / `rootfs_data`**
  - 24.10 ubinize (`KERNEL_IN_UBI=1`) 产出的卷名是 **`kernel` + `rootfs` + `rootfs_data`**
  - 24.10 里走 TAR 路线的设备（如 h3c-nx30-pro-nmbm）**删掉 `rootdisk`/`bootargs-append`**，即不走 fitblk
  - **→ FUR-602 必须走 TAR 路线**（与 hanwckf 官方实现一致），
    **不能**照抄 24.10 多数设备的 `rootdisk`+`volname="fit"` 写法
  - TAR 路线下 `&chosen` 不要 `rootdisk`；U-Boot 会自己 `boot_from_ubi` 找 `kernel` 卷

### 最终技术方案（已确定）
- **DTS**：24.10 DSA 结构 + `mediatek,nmbm` + SPI 校准 + labels `wan`/`lan1..3`
